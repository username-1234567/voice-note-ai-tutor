# 全局对话 · 待复习筛选 · 搜索全量

日期：2026-10-22

## 先纠正一个理解偏差

上一轮我把"直接对话"做成了"每节课内部对话"——挂在回放页、上下文是那节课的标记。

但那不是要的东西。真实需求是：**从首页进去，随手问一个问题或拍张图，答完存成一条带标题的记录，下次能找回来**。和录音没有关系。

所以这一版是全新的两条表、两个页面。

## 数据

`version 3 → 4`：

```kotlin
@Entity(tableName = "chat_sessions")
data class ChatSession(
    val id: Long, val title: String, val note: String?,
    val createdAt: Long, val updatedAt: Long,
)

@Entity(tableName = "chat_messages", indices = [Index("sessionId")])
data class DirectMessage(
    val id: Long, val sessionId: Long, val role: String,
    val content: String, val imagePaths: String?, val createdAt: Long,
)
```

两个命名上的让步：

- 表名没有沿用 `RecordingChat` 那套（`recording_chats`），因为是全局的、不挂录音
- 类名没用 `ChatMessage`——那个名字已经被 AI 模块的消息模型占了（`com.suitanglu.app.ai.ChatMessage`），重名会让两边的 import 打架

`imagePaths` 用 `\n` 分隔而不是单独建表：一次发多张课件照片问"这几页区别在哪"是常见用法，拆表反而让"哪张图属于哪句话"变难查。

## 对话页

**发图**：`PickMultipleVisualMedia(4)` 选图 → 复制进 `filesDir/chat_images/`。必须复制，`content://` 的读权限是临时的，过一会儿原图就读不到了。

上传时强制 `compressImages = true, compressQuality = 80`——手机原图 12MP，直接 base64 一张就几 MB，一轮对话要传十几秒。

**只发图不说话**是允许的：`text.isEmpty() && images.isEmpty()` 才拦。拍一张题直接问是最常见的用法，强迫用户再打一行字没有道理。

**历史带图**：DeepSeek 的前缀缓存对相同前缀不重复计费，所以历史消息里的图片也一起带上，这样追问"第三步为什么"时它还记得那张图。

**标题生成**：首轮回答完，用一次 `reasoningEffort = "off"` 的调用把问题压成不超过 12 字的标题。

理由：列表里如果全是"这道题怎么做…""这个公式…"这种截断，十几次之后就分不清了。这次调用很便宜（关掉思考、输出十几个字），换的是"能一眼认出来"。

失败就保留创建时的"新对话"，不影响使用。

## 待复习筛选

回放页标记标题右侧加了 `FilterChip`（只在真有星标时出现），点一下只看打了星的。

一个必须一起改的地方：进度条圆点点击会 `animateScrollToItem(MARKER_ITEM_OFFSET + index)`，`index` 来自完整列表。开着筛选时点一个被筛掉的标记，算出来的位置是错的——所以点击时先退出筛选。

## 搜索改成全量

去掉了 `take(3)` / `take(500)`，所有追问原文都进索引。

代价是常驻内存：一学期 100 条录音 × 20 标记 × 3 轮 × 800 字，大约 500 万字 ≈ 10MB 字符串。现代手机扛得住，但这是硬成本。

真要撑不住时的正解不是截断，是上 FTS（`@Fts4(contentEntity = ...)`），检索走 SQL、内存里不用留副本——那时再加。

## 已知缺口

**备份没有包含这两张新表。**

- `BackupManager.merge` 是手写逐表复制，还没加 `chat_sessions` / `chat_messages`
- 导出只打包 `recordings/` 和 `images/`，`chat_images/` 没在里面

所以现在导入备份，对话会整段消失。因为功能刚上线、还没有用户数据，暂时没做；但这笔债必须在发布前还掉——和上一轮 `marker_turns` 漏复制是同一个坑。

## 未验证

打包成功（R8 通过），但安装时设备 USB 断连，**没有装机，v3→v4 的迁移没有真机验证过**。

上一轮的教训还热着：`recording_chats` 就是栽在"迁移建了索引、实体忘了声明"。这次两边都对齐了（`chat_messages` 的 `indices` 与 `index_chat_messages_sessionId` 同名），但没真跑过就还不能算数。

# 追加：渲染预览（1.4.0）

## 场景

DeepSeek 官方 App 里复制出来的回答是一堆 `$...$`、`**`、`|---|---|`，贴到别处看就是乱码。这个页面不调模型、不存数据，只做一件事：**把原文贴进来，立刻看到排好版的样子**。

## 实现

`RenderScreen` 复用对话页的 `MarkdownView`——就是"把对话的渲染搬过来"这个意思，同一个 WebView 渲染器、同一套 KaTeX/Markdown 配置，不重写第二份，避免两边样式漂移。

三个细节：

**输入防抖 300ms**。`MarkdownView` 每次刷新都要重跑一遍 WebView 的 `loadData`，逐字符跟着打字会明显卡。所以输入和渲染用两份状态，停顿 300ms 才同步。

**粘贴按钮**。从 DeepSeek 复制完过来，直接点一下比长按输入框再选粘贴快。

**示例**。空状态给一个"填个示例"，里面同时含公式、列表、表格、引用——用户一眼就知道这页能干什么，也顺便验证渲染器对这四类的支持。

入口在设置页，"数据与存储"下面。
