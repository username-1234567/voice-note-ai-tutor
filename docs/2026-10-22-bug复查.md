# 复查：这批新功能里的 bug

日期：2026-10-22
范围：本轮四批改动（长按快拍 / 课后修图 / 思考强度 / 整节归纳）
结果：修复 12 处，其中 4 处会导致崩溃或数据错误。

---

## 严重：会崩或写坏数据

### 1. Room schema 校验会让老用户升级即崩

`Marker.needsReview` 的迁移写的是：

```sql
ALTER TABLE markers ADD COLUMN needsReview INTEGER NOT NULL DEFAULT 0
```

但实体只有 `val needsReview: Boolean = false`，没有声明 `defaultValue`。

Room 启动时会拿实体生成的 `TableInfo` 和实际表结构逐列比对，**包括 `dflt_value`**。实体侧是 null、实际是 `"0"`，比对失败就抛：

```
Room cannot verify the data integrity.
```

这不会在编译期报错，也不会在新装用户身上出现——只有升级上来的那批人会崩，第一帧就闪退。

修复：

```kotlin
@androidx.room.ColumnInfo(defaultValue = "0")
val needsReview: Boolean = false,
```

全新安装时 Room 生成的建表语句也会带上 `DEFAULT 0`，两边一致。

> 教训：给已有表加非空列必须 `DEFAULT`，那就必须在实体上同步声明 `@ColumnInfo(defaultValue = ...)`。编译器不会提醒这件事。

### 2. 恢复录音的通知被调用了 N+1 次

`RecordApp.recoverUnfinishedRecordings()` 里，替换代码时把 `notifyRecovered` 写进了 `for` 循环，而循环外原本的那次调用还在：

```kotlin
for (rec in unfinished) {
    ...
    container.recordingRepository.notifyRecovered(unfinished.size)  // ← 在循环里
}
if (unfinished.isNotEmpty()) {
    container.recordingRepository.notifyRecovered(unfinished.size)  // ← 又调一次
}
```

恢复 3 条录音会调 4 次。因为 `recoveredCount` 是 StateFlow、值相同时不触发重组，实际表现不明显，但这是明确的实现错误。

### 3. 长按快拍会把"上次没保存的图"一起存进去

`saveQuickMarker` 原本是"把图加到 `_pendingImages`，再调 `saveMarker`"。而 `saveMarker` 保存的是**整个 pending 列表**。

于是：面板里拍了一张 → 关掉面板（没保存）→ 长按快拍 → 新标记里出现两张图，其中一张是用户以为已经放弃的。

修复：`saveQuickMarker` 只提交自己那一张，不经过 pending 列表。为此把保存逻辑抽成 `persistMarker(recordingId, offsetMs, images, text, clearPending, onDone)`。

### 4. 关掉标记面板不清理暂存图

`ModalBottomSheet` 的 `onDismissRequest` 只清了文字，没清图：

```kotlin
onDismissRequest = {
    showMarkerSheet = false
    markerText = ""
    vm.discardPending()   // ← 新加
}
```

这是 #3 的成因。两个都修才不会互相掩护。

## 中等：功能不对但不崩

### 5. 星标连点两下等于没点

原来的写法是"把 `marker.needsReview` 取反再写回"。连点两下时，第二次读到的还是重组前的旧值，于是两次都写成同一个值。

改成让 SQL 自己翻转：

```sql
UPDATE markers SET needsReview = CASE WHEN needsReview = 1 THEN 0 ELSE 1 END WHERE id = :id
```

### 6. 改完图，旧讲解还挂在那里

`replaceMarkerImage` 把标记退回 `AI_PENDING`，但没有删 `marker_turns`。展开卡片仍能看到基于**旧图**生成的整段讲解——图和讲解对不上，比空着更误导。

修复：同时 `deleteByMarker(markerId)`。

### 7. 每次提问都读一遍全库

`buildCourseContext()` 用的是 `markerTurnDao().getAll()`，`SELECT *` 不带条件，然后在内存里 filter。

对话是连续动作，问三句就读三遍全表。新增按录音 join 的查询：

```sql
SELECT t.* FROM marker_turns t INNER JOIN markers m ON t.markerId = m.id
WHERE m.recordingId = :recordingId
```

### 8. 搜索索引体积失控

给 `searchText` 加多轮对话时，忘了截断——每个标记的所有轮次、每轮全文都拼进去。

100 条录音 × 20 标记 × 5 轮 × 1000 字 ≈ 1000 万字符，而且**每次 Room 发射都会全量重建**。

修复：每个标记只取最近 3 轮，问题截 200 字、回答截 500 字。

### 9. 静音计时跨暂停累计

`checkSilence` 在 `!active`（暂停/被打断）时直接 `return`，`quietMs` 保留原值。

于是"静音 50 秒 → 暂停一整节课 → 恢复 10 秒"会立刻弹提醒。暂停期间不该计入，恢复后要重新计时。

### 10. 三处文案还在说"自动发送"

取消自动发送之后：

| 位置 | 原文案 |
|---|---|
| 标记卡状态 | "待发送：录音结束后将自动发送" |
| 录音页摘要 | "N 个标记，录音结束后将自动发送 AI 讲解" |
| 首页空状态 | "录音结束后会自动把图片发给 AI 讲解" |

前两处在流程里，用户会照着想；第三处是新用户的第一句话。全部改写为"课后确认图片后手动发送"。

# 第二轮：发送链路与备份

上面 12 处修完之后继续往下挖，又发现 8 处。

## 严重

### 13. 导入旧备份必然失败

`BackupManager.openImportedDb`：

```kotlin
Room.databaseBuilder(context, AppDatabase::class.java, name)
    .createFromFile(file)     // ← 备份文件可能是 v1 / v2
    .allowMainThreadQueries()
    .build()                  // ← 没有 addMigrations
```

备份里是旧版 schema 的 `app.db`。Room 打开它时发现版本对不上、又没注册迁移，直接抛：

```
A migration from 2 to 3 was required but not found
```

用户看到的就是"导入失败"，而备份本身是好的。

这是**升级之后才会暴露**的问题：新版 App 配旧版备份，必现。修复：把迁移提成 `AppDatabase.ALL_MIGRATIONS`，`get()` 和导入共用同一份。

### 14. 单条重发能把同一个标记写出两条首轮对话

`sendSingle` 没有 `busy` 保护：

```kotlin
suspend fun sendSingle(markerId: Long): Boolean {
    val marker = db.markerDao().getById(markerId) ?: return false
    return ensureTurn0AndGenerate(marker)
}
```

批量发送进行中，用户点某条的"重新生成"：两个协程同时查 `orderIndex == 0` 的轮次，都查不到，于是**各插一条**。同一条标记出现两条首轮，`_streaming` 也会被两边交替覆盖。

修复：`sendSingle` 也走同一个 `busy` 原子位。

## 中等

### 15. 生成成功的任务从不从 map 里摘掉

```kotlin
coroutineContext[Job]?.let { activeTurnJobs[turn.id] = it }
try {
    ...
    return true      // ← 成功路径没有 remove
} catch (e: CancellationException) {
    activeTurnJobs.remove(turn.id)   // 只有取消和失败才移除
}
```

`ConcurrentHashMap` 只增不减。每次成功生成留一个已完成的 Job（还挂着 buffer 引用）。用久了是稳定的内存增长。

### 16. 流式对话逐 token 重渲染

`MarkdownView` 的 `update` 每次重组都会把**整段文本**重新丢给 WebView：

```kotlin
update = { wv -> wv.evaluateJavascript("window.render(...)", null) }
```

标记讲解的流式路径有 300ms 节流，而我新写的提纲和对话是 `_chatDraft.value += delta`——每个 token 一次重组、一次完整重渲染。长回答会卡成幻灯片。

修复：两份草稿都改成攒 300ms 再推。

### 17. 对话历史全量渲染

`chats.forEach { ... }` 在卡片里把全部历史铺开，而每条 AI 回答都是一个 WebView 实例。

20 轮对话 = 20 个 WebView 同时存在，内存和滚动都会崩。修复：只渲染最近 20 条，多了给一行提示。

### 18. 改图后 `aiResponse` 清不掉

`updateAi` 的 SQL 是 `aiResponse = COALESCE(:response, aiResponse)`——传 null 表示"保留原值"。`replaceMarkerImage` 想把标记退回待发送并清空讲解，但实际只改了状态：

```
状态 = 待发送
aiResponse = 基于旧图的旧讲解   ← 自相矛盾
```

新增 `setAiState`（不走 COALESCE）真正置空。

### 19. 请求日志表无限增长

每次生成写一条 `ai_request_logs`，成功时带最多 20KB 的回答，而且**只有删除录音时才清理**。

1000 次生成 ≈ 20MB。而备份是整库打包，用户会看到备份文件莫名其妙越来越大。

修复：启动时 `trim(200)`，只留最近 200 条。

## 小

- `settings.generalConfigNow()` 在同一行被调用两次（两次读 DataStore，且可能拿到不同快照）

## 这轮查过、没问题的

| 位置 | 疑虑 | 结论 |
|---|---|---|
| `ChatMessage` 复用同一组图片 File | 会不会重复 base64 编码 | 只有 `orderIndex == 0` 的那条带图，而它只出现一次 |
| `sendQueue` 的 `skipped` 计算 | 部分失败时统计会不会错 | `total - ok - failed`，失败那条已计入 failed，正确 |
| `followUp` 的 `orderIndex` | 并发追问会不会撞号 | 会撞，但排序是 `orderIndex ASC, id ASC`，不会错乱 |
| `generateTurn` 的重复输出检测 | 会不会误判正常内容 | 需连续 20 个完全相同的 delta，`-----` 这类分隔线到不了 |
| `importFrom` 线程 | 会不会 ANR | 整个方法包在 `withContext(Dispatchers.IO)` 里 |

# 第三轮：数据生命周期

前两轮看的是"代码怎么跑"，这轮看"数据怎么活"——谁创建、谁复制、谁该删。这三个环节都出问题了。

### 20. 导入备份会丢掉所有多轮对话

`BackupManager.merge` 是手写的表复制逻辑，只处理了四张表：

```kotlin
db.recordingDao().insert(...)
db.markerDao().insert(...)
db.markerImageDao().insertAll(...)
db.pauseEventDao().insert(...)
```

`marker_turns` 从 v2 就存在，**一直没被复制过**。加上我这轮新增的两张表，一共漏了三张：

| 表 | 导入后果 |
|---|---|
| `marker_turns` | 所有追问和 AI 回答消失（首轮还能靠 `marker.aiResponse` 兜底显示） |
| `recording_digests` | 复习提纲没了，要重新生成 |
| `recording_chats` | 整节对话全丢 |

用户视角就是"导入成功，但我的对话都没了"。

修复：在合并事务里补三段，`marker_turns` 用 `idMap` 把旧的 markerId 映射到新的。

> 教训：`merge` 这种手写逐表复制，新增表时**没有任何编译期提醒**。以后再加表必须回来改这里。

### 21. 彻底删除会留下孤儿数据

`deleteForever` 删了音频、图片、图片记录、请求日志、标记、暂停事件、录音——同样漏了三张表。

后果比 #20 更糟：

- `marker_turns` 里留下指向已删除标记的行，数据库只增不减
- `recording_chats` 里的对话**在用户已经点了"彻底删除"之后仍然存在**

第二点是隐私问题：用户以为删干净了，实际上聊天记录还躺在数据库里。

修复：循环里补 `markerTurnDao().deleteByMarker(m.id)`，事务尾部补 `recordingDigestDao().delete()` 和 `recordingChatDao().clear()`。

### 22. 导入备份会清空已经填好的 API Key

```kotlin
settings.setAiConfig(s.ai)   // 整体覆盖
```

如果备份导出时用户还没配 Key（`apiKey == ""`），后来才配好，再导入那份旧备份时——**Key 被覆盖成空字符串**。

用户不会立刻发现，直到下一次录音，全部标记变成"未配置 API Key"。

修复：备份里的 Key 为空时保留本地的。

```kotlin
val localAi = settings.aiConfigNow()
val restoredAi = if (s.ai.apiKey.isBlank()) s.ai.copy(apiKey = localAi.apiKey) else s.ai
```

### 23. 系统大字体下按钮文字会顶出容器

"拍照并标记（已 12 个）"放在固定 `height(56.dp)` 的容器里，没有 `maxLines`。系统字体调到 1.3 倍以上时文字换行，超出部分被裁掉半个字。

修复：`maxLines = 1` + 省略号。这种情况在自绘按钮里特别容易漏——`Button` 内部有默认的紧凑换行处理，自己拿 `Box` 拼就得自己管。

## 这轮查过、没问题的

| 位置 | 疑虑 | 结论 |
|---|---|---|
| 导出 zip 重名 | `putNextEntry` 遇重复 entry 会抛 `ZipException` | 录音和图片都经 `copyWithRename` 生成唯一名，不会重名 |
| `observeActive` 是否过滤回收站 | 回收站内容会不会混进首页和搜索 | SQL 带 `deletedAt IS NULL`，不会 |

# 第四轮：录音服务

前三轮都在"读"和"写"上，这轮看数据源头——`RecordingService`。找到两处，都在主线程上。

### 24. MediaRecorder 创建失败时会泄漏

```kotlin
recorder = MediaRecorder(applicationContext).apply {
    ...
    prepare()      // ← 这里抛异常
    start()
}
```

`apply` 内部抛异常时，**赋值语句根本不会执行**，`recorder` 保持 null。catch 里调 `releaseRecorder()` 拿到的是 null，什么也没释放——那个已经 new 出来的 `MediaRecorder` 连同它的 native 资源就没人管了。

触发条件很常见：麦克风被别的应用占用、权限在录音途中被撤销，`prepare()` 就会失败。后果是这台机器之后每次录音都可能失败，直到进程重启。

修复：先建局部引用，失败时 release 它。

```kotlin
val mr = MediaRecorder(applicationContext)
try {
    mr.apply { ...; prepare(); start() }
} catch (e: Exception) {
    runCatching { mr.release() }
    throw e
}
recorder = mr
```

### 25. MediaRecorder.stop() 跑在主线程

`stopRecording()` 是 `onStartCommand(ACTION_STOP)` 直接调进来的，也就是主线程。而它第一件事就是 `releaseRecorder()`：

```kotlin
private fun releaseRecorder() {
    recorder?.stop()      // ← 写 MP4 的 moov atom，90 分钟的录音几百毫秒到几秒
    recorder?.release()
}
```

`MediaRecorder.stop()` 不是简单的收尾，它要把整段录音的索引（moov）写完并 flush 到磁盘。一节课 80MB 的录音，在低端机上完全可能超过 5 秒的 ANR 阈值。

修复：主线程只做"把对象摘下来"，`stop()` / `release()` 和后续收尾一起扔到 `scope`（`Dispatchers.Default`）。

```kotlin
val toRelease = recorder
recorder = null          // 立刻置空，见下
releaseFocus()
timerJob?.cancel()
scope.launch {
    toRelease?.stop(); toRelease?.release()
    RecordingBus.update(null)
    finalizeRecording(...)
}
```

**这里有个连锁反应必须一起处理**：如果只是把释放挪走、不同时把 `recorder` 置空，那么在释放完成前（最多几秒）`startRecording()` 的第一行

```kotlin
if (recorder != null) return
```

会直接 return——用户点了"开始"，什么都不会发生。所以必须先把属性摘下来，再让后台去释放那个局部引用。

### 一个观察：录音抢的是独占音频焦点

`requestAudioFocus()` 用的是 `AUDIOFOCUS_GAIN`，会让其他应用（包括**本应用自己的回放页**）让出焦点。

于是"录音进行中，回首页点开一条旧录音听"这个操作会导致：播放器请求焦点 → 录音收到 `AUDIOFOCUS_LOSS` → 自动暂停。

这个行为本身没错（录音优先），但它是隐式的：用户在听回放，不会想到录音被暂停了。没有改，记在这里作为已知交互。

---

## 这轮查过、没问题的

| 位置 | 疑虑 | 结论 |
|---|---|---|
| `onStartCommand` 返回 `START_NOT_STICKY` | 服务被杀后系统会不会拉起一个空壳 | 不会；恢复由 `RecordApp.recoverUnfinishedRecordings` 负责 |
| `onDestroy` 里 `scope.cancel()` 再 `releaseRecorder()` | 会不会打断收尾 | 正常路径 `stopSelf()` 在协程末尾，不会被 cancel 到；异常路径资源随进程回收 |
| `startRecording` 的 `pauseRequested` | 停止后误点暂停，下次录音会不会一开就停 | 启动开头无条件重置，不会 |
| `PlaybackViewModel.onCleared` | 播放器有没有释放 | 有，`release()` + ticker.cancel() |

# 第五轮：真机安装暴露的问题

前四轮都是静态看代码，加上一次 `python sqlite3` 的 SQL 语法验证。真机一装，前四轮"看起来没问题"的地方立刻倒了一个。

## 26. 迁移真的崩了（而且是我自己埋的）

设备上是 v1.3.1（schema v2），装新版第一次启动：

```
FATAL EXCEPTION: DefaultDispatcher-worker-4
java.lang.IllegalStateException: Migration didn't properly handle:
    recording_chats(com.suitanglu.app.data.db.RecordingChat).
```

把 Room 打印的 Expected / Found 拉出来对比：

```
Expected:  indices = { }                          ← 实体没声明索引
Found:     name = 'index_recording_chats_recordingId'   ← 迁移里建了
```

**原因**：`MIGRATION_2_3` 里我写了

```sql
CREATE INDEX IF NOT EXISTS `index_recording_chats_recordingId` ON `recording_chats` (`recordingId`)
```

但 `RecordingChat` 实体只有 `@Entity(tableName = "recording_chats")`，没有 `indices = [...]`。

Room 的 schema 校验**连索引也一起比**，"实际有、实体没声明"同样判为不匹配。

修复：

```kotlin
@Entity(tableName = "recording_chats", indices = [androidx.room.Index("recordingId")])
```

顺带核对了其余七张表：`marker_turns` 早就声明了 `indices = [Index("markerId")]`，其余表都没索引，与迁移一致——只有我新加的这张漏了。

## 为什么前三轮都没发现

第一轮我判断过这个风险，检查了**列**的 `defaultValue`，加了 `@ColumnInfo(defaultValue = "0")`。

然后用 `python sqlite3` 跑了一遍迁移 SQL，确认：列类型对、NOT NULL 对、`dflt_value = '0'`、索引名对。

这些都对——**但 sqlite 验证的是"这个 SQL 能不能跑"，不是"Room 认不认这个结果"**。Room 的期望值来自实体注解，两边是否一致只有它自己的 `TableInfo` 校验说了算，而那玩意儿只在真机首次打开数据库时执行。

一句话：**静态验证能证明 SQL 合法，证明不了 schema 等价。**

## 27. 顺带：签名配置是从 CI 拷过来的 Linux 路径

第一次构建产出的是 `app-release-unsigned.apk`，`signingConfig` 没生效。查 `local.properties`：

```
signing.storeFile=/home/a/signing/suitanglu-v2.jks
```

是 Linux 路径（应该是从 CI 环境直接拷的），Windows 上 `File(...).exists()` 为 false，签名配置整块被跳过，但不报错——构建照样成功，只是产物没签名。

改成实际路径 `C:/Users/z2036/AndroidStudioProjects/signing/suitanglu-v2.jks` 后正常。

这个坑值得记：**签名配置缺失时 Gradle 不报错**，只在 `assembleRelease` 的产物文件名上体现（`-unsigned`）。
